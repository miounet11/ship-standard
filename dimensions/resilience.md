# 长跑自动化：容错方法

从长跑自动化排障里抽出的做法。不绑定某一家供应方或某一个站点；换平台、换页面、换运行时，同一套步骤仍然适用。

核心原则：**先看页面/接口原文，再决定动作。不同失败不能合成同一种处理。任何一层卡住都要能换路，不能停机。**

产品对照见 [examples/long-running-signup.md](../examples/long-running-signup.md)。

分类语料（≥20 条真实原文）和主路径四步是全产品合同，权威是 `LAUNCH-2` / `LAUNCH-1`。本纬度只锁长跑特有的供应方、归一、采购、主机与日志。

---

## 1. 先取证，再归类

不要凭印象说「对方不认这种资源」。先存失败现场：

- 当前 URL、可见正文、按钮文案、输入框 name
- 刚调用过的接口状态码和摘要（不含密钥）
- 这一步之前获取了什么、点了什么、等了多久

用原文做分类器，禁止把「没看到验证码框」当成唯一错误。同一句「失败」背后至少要能拆出：

| 类型 | 典型原文 | 正确动作 |
|------|----------|----------|
| 资源被拒 | 域名/号段已被拒绝，请换一个 | **立刻退役 + 退款/申诉 + 拉黑该资源**，换下一个 |
| 频控 | 验证码过多，N 分钟后再试 | **停发、冷却 N 分钟**，去收件箱捞已有码，不重提 |
| 已发出 | 我们已向 xxx 发送了一次性代码 | **留在当前页等**，加长收码窗口，不关窗重提 |
| 码错 | validation code is invalid | **再拉一次最新码填一次**；仍错再退役 |
| 已占用 | 已被注册 / account exists | 退役 + 按「已使用」申诉 |
| 通道问题 | 代理失败、地区不可用、隧道失败 | **换通道**，已获取的资源不动 |
| 基础设施 | 接口超时、运行时起不来、内存不够 | **退避 / 降并发 / 延后副作用**，不把业务资源判死 |

分类器要写成纯函数并配单元测试，把真实报错句子贴进测试里。

---

## 2. 动作表：一种问题只做一种事

每个分类必须落到且只落到一种动作：

- **refund**：对方明确说资源不可用 / 已占用 / 码错且刷新无效 → 向供应方申诉，永不回池
- **cooldown**：对方明确给了等待时间 → 按分钟停用该资源，同时获取下一份继续跑
- **wait**：对方说「已经寄出」→ 加长等待，不重放「提交」
- **retry-channel**：网络/代理/运行时启动 → 换出口或重启动，资源保留
- **shed**：CPU/内存过高 → 降线程或暂停开新窗口
- **defer**：主流程已成功、下游导入失败 → 本地落盘，稍后补推

禁止：

- 用「重试提交」去处理频控（会加重「验证码过多」）
- 用「整类停买」去处理单个坏资源（会变成只打最贵的一种）
- 用「熔断禁止新获取」去处理池里几份脏资源（会空转到天亮）

---

## 3. 提交动作必须精确

UI 自动化里，子串匹配会点错按钮。例如「注册」会点到「使用邮箱注册」。

方法：

- 入口按钮和提交按钮用**整段文案相等**，不要子串匹配
- 提交后读页面，再决定下一步；不要固定「等 N 秒没有码框就再点一次提交」
- 同一资源在冷却期内禁止再次触发「发送验证码」

这条可以套到任何「获取验证码 / 登录 / 下单」表单。

---

## 4. 资源身份要归一

供应方卖的「变体」在目标站可能是同一账户。例如邮箱去点号、别名域等价、`+tag` 可丢弃。

方法：

- 获取或列出资源后先算 `normalizeKey`
- 同一 key 已在用或已冷却 → 不提交、不连发
- 拉黑的是 **域名 / 号段 / 归一 key**，不是整类商品

采购按**件数比例**交错，不要按金额补齐（金额补齐会在便宜类型失败后把预算全砸到贵的一类）。类型可以**软暂停**（例如连拒 3 次暂停 15 分钟），不要永久熔断。

---

## 5. 等待策略按「对方已经做了什么」来

| 对方状态 | 我们等多久 | 要不要重提 |
|----------|------------|------------|
| 还没提交成功 | 短等 + 检查是否点错按钮 | 最多精确再点一次提交 |
| 已寄出验证码 | 2–3 分钟，轮询收件箱和邮件列表 | 不重提 |
| 频控 N 分钟 | 冷却 N 分钟；同时捞旧信 | 不重提 |
| 收码接口抖动 | 单次请求超时重试，总窗口不变 | 不重提 |

收码要同时打「最新验证码」和「列表」（含未匹配/垃圾箱）。供应方商业化产品通常两套接口都有。

---

## 6. 业务错误 vs 基础设施错误

两套分类器，不要混用。

**业务层**（页面原文）：决定这份资源退、冷、等、换。

**基础设施层**（进程/主机/HTTP）：

- 供应方 / 导入方 / 通道池：超时 + 有限次退避；5xx/429 当通道故障
- 运行时拉不起：启动前看负载，失败再试一次，再不行换通道、降线程
- CPU/内存：按 `load/核数` 和剩余内存 **降并发或暂停开新窗口**
- 下游导入失败：主产物已落盘则算成功，导入写入 `pending` 稍后补

单次业务尝试要有**硬顶时间**（例如 4 分钟），超时只换通道，不把资源判死。

---

## 7. 保底：任何一层都不能卡死整场

按空闲时间升级，而不是按失败次数关停：

1. **线程自己崩了**：外层兜住，数秒后继续；未捕获异常只打日志
2. **数分钟无进展**：刷新通道池
3. **更长时间无进展**：降回最少线程，解开类型软暂停
4. **余额不足 / 暂时买不到新资源**：指数退避（秒级到 1 分钟），不要退出进程
5. **池里全是冷却中的资源**：照样允许新获取，一边等一边往前走
6. **看门狗与业务循环解耦**：定时器不挡住正常停机

停机只认明确的 STOP 信号，不认「最近全失败」。

## 8. 门禁（换到别的软件时按这个做）

分类语料和主路径四步是全产品合同，走 `LAUNCH-2` / `LAUNCH-1`，本纬度不再另判一条。

- [ ] `RESIL-3` 列出供应方能力（获取、指定类型、查库存、收码、列表、申诉原因码），每种失败对上一个原因码
- [ ] `RESIL-4` 归一规则写清：哪些变体在目标站是同一身份
- [ ] `RESIL-5` 采购比例用计数交错；失败拉黑到域/号段，类型只软暂停
- [ ] `RESIL-6` 启动、HTTP、导入全部带超时和有限重试；导入失败不回滚已成功的主产物
- [ ] `RESIL-7` 主机负载采样进看门狗；内存过低先减窗口再暂停
- [ ] `RESIL-8` 日志必须能区分：`skip`（退役）、`cooldown`、`pause-type`、`launch-fail`、`host shed`、`watchdog`、`deferred`
