# 主路径验收：真实拓扑、同版本、能再走一遍

功能矩阵打满，不等于用户能走完主路径。收尾阶段只认：**指定拓扑 + 两端同号 + 主路径逐步勾完 + 退出后还能再进**。

配套阅读：[launch](./launch.md) 阶段 4–6 · [diagnose](./diagnose.md) · [quality-kernel](./quality-kernel.md)。

---

## 一句话

**失败禁止写「联调完成」。主路径没勾完、拓扑是反模式、两端版本不一致，都不算收尾。**

---

## 何时用

- 双端 / 多端 / 云 + 客户端产品发版前
- 用虚拟机、嵌套环境、本机互控当「验收」时
- 仓库已经发版，但没人用正式包把主路径走完

---

## 主路径最少 7 步

按产品改字，不要改结构：

| # | 步骤 | 通过标准 |
|---|------|----------|
| 1 | 各端登录同一身份，列表互见 | 不必狂点刷新 |
| 2 | 按产品规定的方向发起 | 只开一个业务窗；文案无人话以外的协议词 |
| 3 | 主任务可操作 | 点得准；无粘滞的独占状态 |
| 4 | 主产物可读 / 可用 | 好条件不锁死低档 |
| 5 | 一项附加能力 | 例如小文件、剪贴板，证明通道不是空壳 |
| 6 | 断开 | 无残留；对端仍在线或状态可解释 |
| 7 | 再进 | 比首次更快或至少能进，不带上次脏状态 |

任一步失败：停在这一步定位，不要继续打后面的勾。

---

## 拓扑：只验有产品意义的路径

验收拓扑必须对应**真实用户会怎么用**。下列是反模式：

| 反模式 | 为什么污染验收 |
|--------|----------------|
| 嵌套互控（A 在 B 的虚拟机里再控宿主 B） | 递归画面、输入叠加、内存双倍、假糊假失败 |
| 本机其它同类软件同时开着 | 抢焦点、抢坐标，分不清是产品 bug |
| 一端 dev、一端正式签名包 | origin / CSP / API base 不同 |
| 两端 version 不一致 | 修在新码，败在旧包 |
| 用模拟器低帧当产品失败 | 分场景；联调环境 ≠ 用户环境 |

合法例外必须写成单独任务（例如「真机双机反向」），不得当作日常默认。

---

## 同版本与用户通道

```
仓库 version
   = 各端安装包 version
   = 用户能拉到的 OTA / 商店 / 下载页
```

落后超过一个次版本，[quality-kernel](./quality-kernel.md) `KERNEL-5` 失败。本地构建成功但没人装上，验收无效。

---

## 长测（发版后仍要做）

主路径是分钟级冒烟。收尾还要有一个业务周期：

- 指定拓扑跑满约定时长（例如 30 分钟）
- 通过标准预先写死：未永久不可用、无残留、好条件不锁死低档、退出可再进
- 记录时间点，不写「感觉还行」

没做长测可以内测，不能把「已上线」写进对外材料。

---

## 人话与入口

主路径上的文案和入口也是验收项：

- 阶段文案只有一套（连接中 / 进行中 / 恢复中 / 已结束）
- 设置只有一个常驻入口；禁止第二套把手抢点击
- 错误说人话：内存不足、通道不通、网络不通；不说内部算法名

---

## 验收句

1. 主路径 7 步有勾选记录，失败步可指出层（见 diagnose）。
2. 日常验收只走一份写死的拓扑，反模式不进「已通过」。
3. 各端安装包 version 一致，且与用户通道一致。
4. 退出后再进不携带粘滞状态。

---

## 门禁

- [ ] `PATH-1` 主路径 7 步已勾，或明确停在失败步
- [ ] `PATH-7` 验收拓扑是真实用户路径，反模式环境不计入通过
- [ ] `PATH-3` 各端同 version，用户通道已对齐
- [ ] `PATH-4` 已排除本机竞品 / 自动化干扰
- [ ] `PATH-5` 文案无人话以外的协议词；设置入口唯一
- [ ] `PATH-6` 有长测记录或明确标注「仅冒烟、未长测」

## 已废止

- `PATH-2` → `PATH-7`：嵌套互控是反模式的一个例子，不再当全产品合同句

---

## 禁止

- 功能矩阵打满就写联调完成
- 在反模式拓扑上修「假 bug」并当作产品修复发版
- 一端新包一端旧包对打
- 用开发机 `dev` 代替签名包验收

---
