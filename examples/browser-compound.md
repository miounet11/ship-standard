# 例子：桌面浏览器产品如何把产品力做复利

对照 [compound](../dimensions/compound.md) 与 [probe](../dimensions/probe.md)。只写工作方式，不写对抗实现、探测站点操作或补丁细节。

---

## 他们先做对的顺序

| 阶段 | 做了什么 | 门禁 |
|------|----------|------|
| 看见 | 北极星 3–5 条；路线图只服务它们 | `COMPOUND-1` |
| 看见 | 路线图、风险册、门禁、规格、生成的状态页 | `COMPOUND-2` |
| 写成合同 | 每个已宣称的核心能力有基线文件 | `COMPOUND-4` |
| 发布 | 打开的 S1 为 0，否则通道是 beta | `COMPOUND-5` |
| 证据 | PR / 发版材料能看见诊断到反思的七步 | `PROBE-1` |
| 范围 | 本范围门禁写清 warn 还是 block | `PROBE-2` |
| 先红后绿 | 新行为有探针；S1 修复有回归 | `PROBE-3` |
| 改得动 | 入口行数、view 不发 IPC，用架构探针锁住 | `PROBE-4` |
| 基线 | 改阈值和改代码同一变更，或确认未回退 | `PROBE-5` |
| 风险 | 同一变更把新缺口补进风险册 | `PROBE-6` |

北极星用来否决「只因为别人有」（`COMPOUND-1`）。怎么执行七步看 [build-standard](https://github.com/miounet11/build-standard)，本仓只验收证据（`PROBE-1`）。

---

## 不要从这份例子里学的

- 不要把外部评分网站清单抄进自己的规格，除非那就是你的产品合同
- 不要跳过「看见 / 改得动」去抄后半段能力名
- 不要把病例长度当成架构
- 不要写密钥、真实账号、主机地址
